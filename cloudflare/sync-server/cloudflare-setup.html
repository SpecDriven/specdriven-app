Set up the SpecDriven sync server on Cloudflare

One deployment gives every data repository its own live-sync server, open only to people who can push to that repository on GitHub. Git stays the source of record; this makes edits travel between running apps within moments.

Before you rely on this page: the server has been run on a developer machine with Cloudflare's local runtime (wrangler dev) and a stand-in for GitHub. It has not yet been deployed to a real Cloudflare account, so the deploy steps below follow Cloudflare's documented commands but have not been run end to end. The app side ships with pull request SpecDriven/specdriven-app#485; an app released before it is merged does not understand the {repo} address.

What you need

  • A Cloudflare account. The free plan is enough to start: it includes Durable Objects with SQLite storage, with 5 GB of storage for the account.
  • Bun installed, and a checkout of the specdriven-app repository that contains cloudflare/sync-server.
  • Data repositories hosted on GitHub. One deployment checks against one GitHub (github.com unless you change it, see Options).

Deploy the server

  1. Install the server's tools

    This installs Wrangler, Cloudflare's command-line tool, into the folder.

    cd cloudflare/sync-server
bun install

  2. Sign Wrangler in to Cloudflare

    A browser window opens and asks you to allow Wrangler to act on your account.

    bunx wrangler login

  3. Deploy

    The first deploy may ask you to choose a workers.dev subdomain for your account. It creates the Worker named specdriven-sync and its Durable Object class.

    bunx wrangler deploy

    Expect: the Worker's address at the end of the output, such as https://specdriven-sync.<your-subdomain>.workers.dev. Keep it for the next steps.

  4. Set the signing secret

    The server signs each access pass with this secret. Until it is set, the server refuses every request for a pass. This command generates a random secret and stores it on the Worker without showing it or writing it to a file.

    openssl rand -base64 32 | bunx wrangler secret put TICKET_SECRET

  5. Check that it answers

    Replace the address with yours.

    curl https://specdriven-sync.<your-subdomain>.workers.dev/.well-known/specdriven-sync

    Expect: {"githubHost":"github.com","ticketSeconds":3600}

Point the app at it

Each person does this once, in their own app.

  1. Sign in to GitHub in the app

    The app proves your write access with your GitHub sign-in: the one the app holds, or the GitHub CLI's when the app is set to use it. The data repository's origin must be the GitHub repository.

  2. Enter the address in Settings

    Open Settings, turn on Live sync server (optional), and enter your Worker's address starting with wss:// and ending with /{repo}. Type {repo} exactly as written; the app replaces it with the owner and name of whichever data repository is open.

    wss://specdriven-sync.<your-subdomain>.workers.dev/{repo}

  3. Confirm it connected

    The app's log gains a line naming the repository's own server:

    [netsync] syncing with wss://specdriven-sync.<your-subdomain>.workers.dev/<owner>/<name>

    The desktop app writes its log to ~/.specdriven/logs/specdriven.log. With two people connected, an edit one of them saves appears on the other's screen within about a second.

How access works

  • The app first asks the server which GitHub it checks against. If that is not the GitHub the data repository is on, the app stops and sends nothing.
  • The app then sends your GitHub token to the Worker once, over HTTPS. The Worker asks GitHub whether that token can push to the repository and keeps nothing.
  • If it can, the Worker returns a pass for that one repository, valid for an hour. Read access is not enough.
  • The app renews the pass in the background. A connection closes when its pass runs out, so someone who loses write access on GitHub is out within the hour.
  • The token is only ever sent to an address that contains {repo} and starts with wss://. A plain server such as wss://sync.automerge.org never receives it.

Options

These are in cloudflare/sync-server/wrangler.jsonc. Run bunx wrangler deploy again after changing them.

NameDefaultWhat it does
GITHUB_HOSTgithub.com The GitHub whose repositories this server serves.
GITHUB_API_URLhttps://api.github.com That GitHub's REST API. For GitHub Enterprise Server it is usually https://<host>/api/v3, and Cloudflare must be able to reach it from the internet.
TICKET_SECONDS3600 How long a pass lasts. Shorter means lost access takes effect sooner and GitHub is asked more often. A value under 60 is ignored and the default used.

Your own domain. To serve from a domain already on your Cloudflare account instead of workers.dev, add this to wrangler.jsonc and deploy again, then use wss://sync.example.com/{repo} in Settings:

"routes": [{ "pattern": "sync.example.com", "custom_domain": true }]

Changing the secret. Run the secret command from step 4 again. Every outstanding pass stops working at once and each app asks for a new one by itself.

Watching it. bunx wrangler tail streams the server's live log, including the reason whenever it drops a connection.

If it does not connect

The app logs why, on a line starting [netsync] not syncing with. It stays on git sync meanwhile; nothing is lost.

The log saysWhat to do
Write access to the repository is required Your GitHub account cannot push to this repository, or cannot see it. Ask for write access on GitHub.
GitHub did not accept the token Sign in to GitHub again in the app.
The sync server has no TICKET_SECRET set Run step 4 of the deployment.
the sync server checks access on …, and the data repository is on … The server is set up for a different GitHub. Set GITHUB_HOST and GITHUB_API_URL, or use a server deployed for that GitHub.
the data folder has no GitHub repository as its origin The open data folder is not a clone of a GitHub repository, so it has no server to go to.
sign in to … to use the repository's sync server The app has no GitHub sign-in. Sign in, then turn Live sync server off and on again.
the sync server address must start with wss:// The address uses ws://. The app sends GitHub access only over an encrypted connection.
the address does not answer as a SpecDriven sync server The address is wrong, or the Worker is not deployed. Repeat step 5.
the sync server at … could not be reached A network problem. The app tries again every minute by itself.

After a refusal that needs you to change something (access, sign-in), turn Live sync server off and on again in Settings, or restart the app, to make it try again.

Good to know

  • Storage. Each repository's documents live in its own Durable Object's storage, up to 10 GB per repository. They stay there while the server sleeps. No R2 bucket is needed.
  • Losing the storage loses nothing for good. Every app holds its repository's documents and offers them again on connecting, and git has them all.
  • Running time. "Connected" means the app is open, not that someone is typing: the app connects when it starts and stays connected until it quits. The server does not stay running for that. While nobody is editing it goes out of memory with the connections still open, and Cloudflare bills no running time; the next edit wakes it within a moment. An app left open overnight costs nothing while it sits idle.
  • What it does cost. Running time is billed only while a repository's server is awake, at 128 MB: one hour awake is about 460 GB-seconds. The free plan allows 13,000 GB-seconds a day, about 28 awake hours, and the paid plan includes 400,000 a month, about 868 awake hours, then charges $12.50 per million. Requests are counted too: each connection is one, and every 20 messages a server receives count as one. The free plan allows 100,000 requests a day and refuses further use that day once they are spent; the paid plan includes a million a month, then charges $0.15 per million. Figures from Cloudflare's pricing page on 19 November 2026; check it for current ones.
  • Idle connections. Nothing is sent while nobody edits. If a network silently drops such an idle connection, that app can miss live edits until it connects again, at the latest when its pass is renewed within the hour. Git sync delivers them meanwhile.
  • Not yet checked against GitHub itself. The write-access check relies on the permissions.push field of GitHub's repository response and has only been run against a stand-in.
